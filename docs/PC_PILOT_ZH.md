# 第一台真实实验 PC：服务器与子电脑如何配合

本机是中央服务器；chopper、两台 SMU 和锁相接在另一台 Windows 子电脑上。第一轮只接这一台子电脑，先验证通信和只读采集，再接入小范围实验。无需把生产环境完整复制到服务器。

## 1. 先区分现在能运行的部分与本次要接入的部分

当前仓库已经有中央服务、PC Agent、独立认证、出站轮询、心跳、本地日志和模拟实验的数据回传。**真实 SMU、锁相和 chopper 尚未接入运行时**：当前设备类型只有模拟 laser、rotator 和 spectrometer，不能把配置改成 `real` 就直接运行现有实验代码。

因此，本次接入包含两件事：

1. 复用现有网络框架，让实验 PC 与中央服务器连接。
2. 参考实验 PC 上已经能用的代码，补上具体型号的驱动、允许执行的动作、数据格式和相应的中央任务支持。

网络连通、Agent 在线和真实仪器可控是三个分别验收的结果。架构图中的自主校准、实时科学决策与本地理论计算，不能当作本轮已经实现的硬件功能。

## 2. 两端各自做什么

| 内容 | 中央服务器（本机） | Windows 实验 PC |
| --- | --- | --- |
| 科学任务 | 接收实验目标，准备计划，分析数据 | 执行分配到本机的有限任务 |
| 大模型 | 运行或调用模型；本地模型也在这里 | 不要求安装大模型或填写模型 API key |
| 设备驱动 | 保存驱动版本与设备登记信息 | 调用本机 VISA、SDK 或现有 Python 环境 |
| 仪器通信 | 向该 PC 下发经过检查的高层动作 | 在本机通过 GPIB、USB、串口或网口操作仪器 |
| 实验记录 | 汇总计划、状态、结果和原始数据副本 | 保留本地执行记录和采集数据，再上传 |
| 网络 | 提供 PC 能访问的中央地址 | 主动连接中央，不要求 SSH 或开放入站端口 |

```text
操作者 → 中央服务器：实验目标、参数范围、开始/停止
                    ↓
             经过检查的阶段任务
                    ↓ 任务随子电脑的轮询响应返回
Windows 实验 PC：本地 Agent → 驱动/现有控制库 → 仪器
                    ↓
             本地记录、状态、测量数据
                    ↓ 主动上传
             中央服务器：显示、分析、下一阶段
```

服务器不需要直接访问仪器的 GPIB 地址，也不需要访问子电脑的磁盘路径。仪器地址只由本地驱动使用。网络任务用于慢控制；chopper 的物理参考信号与锁相输入之间的接线仍是独立的信号通道。

## 3. 你先提供的最小信息

无需整理整个生产目录。先提供下面这份简表，以及与这些设备有关的代码即可。

```text
PC 名称：例如 cavity-pc
Windows 版本/位数：
目前可正常运行代码的 Python 路径和版本：
PC 所在网络：与服务器同网段 / 跨网段 / 不清楚

设备           厂商及完整型号     连接方式与本机地址     当前用途
chopper        ...              ...                    ...
SMU 1          ...              ...                    ...
SMU 2          ...              ...                    ...
锁相           ...              ...                    ...

已有代码路径：
相关 SDK / VISA 后端 / 控制软件：
当前设备是否正在被 Notebook 或其他软件使用：
```

两台 SMU 的作用先按现有接线填写，不预先指定其中一台一定施加 gate。chopper 可能是直接通信，也可能通过其他仪器的模拟输出控制；需要从实际型号和接线识别。

代码优先提供：依赖导入、地址设置、连接、状态/读数、参数设置、停止与异常处理。可附上历史身份查询结果，并注明是历史记录。服务器上的参考文件只用于阅读和提取适配逻辑，不直接执行整个 Notebook，也不把参考文件中的地址当成本次实机的已验证地址。

例如你提到的 `subComputer/cavity/Fe-JFET optoelectronic test_Shuang_2.ipynb` 可以作为参考；生产代码、SDK、DLL 和原始数据仍留在子电脑。若没有现成依赖清单，再从原先可用的环境导出，先不升级或重装它。

## 4. 服务器先准备什么

1. 确定子电脑能够访问的中央地址 `server_url`。同一实验网络先使用实际 LAN 地址；跨网络使用已有允许的路由、VPN 或 HTTPS 入口。`127.0.0.1` 在子电脑上指的是子电脑自身。
2. 核对参考代码及具体型号，提取有限动作，分开“只连接/读取”与“复位/配置/开输出”。有些驱动构造函数和 Notebook 初始化单元格本身会写设备，必须检查。
3. 增加对应设备类型、驱动选择、命令与数据 schema，以及中央预检查和本地参数限制。初次先暴露身份、状态和经过验证的读取动作；输出动作后续单独加入。
4. 为这一台 PC 登记独立 ID、凭证和设备清单，生成专用包。中央保存管理员凭证；下发包只带这台 PC 自己的凭证。
5. 启动中央单进程服务，并验证 `/health`。已有配置时使用原配置，不重新 `init` 覆盖或并行建立另一套控制同一设备的服务。

**这些步骤完成后才有真实仪器试点包。** 当前 `labos init` 生成的是两台 PC 的模拟光学演示配置，不是上述四台真实仪器的配置。

## 5. 子电脑需要安装和输入什么

第一次准备：

- 专用 PC Agent 包，放在例如 `C:\LabOS\cavity-pc` 的独立目录。
- 该型号实际需要的 VISA/USB 驱动或厂商 SDK。若现有代码已经正常控制设备，优先复用原驱动及其兼容环境。
- 包内约定的 Python 运行时；如果 SDK 依赖特定 Python 版本、32/64 位或 .NET，应随适配结果选用，不能强行套用通用便携解释器。

不要求安装中央服务、模型、SSH 服务或全部 LabOS 开发工具。首次手动运行成功后，再考虑登录自动启动。

如果子电脑已有大模型 Agent，可以让它阅读 [英文协作文档入口](../src/labos/assets/README_AGENT_KIT_EN.md)，协助检查本机环境、整理代码和交接报告。它与常驻的执行 Agent 分工协作；0.2.2 可使用已配置的 HTTPS 报告通道直接收发，详见 [英文通信指南](../src/labos/assets/COOPERATION_HTTPS_EN.md)；离线时仍可由操作者转交。

子电脑通常只需核对以下内容，专用包可预先填好：

| 输入 | 来源与用途 |
| --- | --- |
| `server_url` | 服务器实际地址 |
| `agent_id` 与该 PC 的 token | 服务器生成；不要多台 PC 共用 |
| 仪器地址与驱动配置 | 按本机实际连接填写 |
| 本地数据目录 | 保存日志、执行记录和原始文件 |
| 装置限制 | 后续启用输出前填写：允许值、compliance、变化速率、停止顺序 |

无需每次启动重新描述所有设备。首次保存装置配置；换仪器、换接线或改变关键限制时再更新版本。

## 6. 包准备好后的两端操作

服务器端先用已经生成的中央配置启动，例如：

```bash
# 在 LabOS 项目目录运行；将配置路径替换为本次实际生成的路径。
.venv/bin/python -m labos central --config deployments/cavity-pilot/central/config.yaml
```

Windows 端先在浏览器打开实际中央地址的 `/health`。然后在已解压的专用包目录运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Doctor.ps1
```

`Doctor.ps1` 检查中央服务、TLS 和该 PC 的认证，不注册 Agent，也不测试仪器。成功后双击 `Start-Agent.cmd`。服务器侧检查 Agent 上线和上报状态。Doctor 通过而 Agent 未启动时，中央不会因此显示实验 PC 已在线。

若网络不通，按中央地址检查 DNS、端口、路由和中央监听，详见 [网络指南](NETWORK_ZH.md)。不需要先解决 SSH。不同仪器程序可能独占连接；测试开始前，应在操作者安排的空闲时段释放相应控制会话，避免旧 Notebook 与新 Agent 同时控制。

## 7. 第一轮怎样测，怎样算成功

### 第一步：只读接入

第一条试点任务建议是：

> 识别这台 PC 上登记的两台 SMU 和锁相，读取经型号核对的当前配置与状态。对锁相记录一段带时间戳的读数；不复位、不改量程或参考配置、不启动 chopper、不改变 SMU 输出。

这里的“读取”需要逐条核对命令含义。例如某些测量命令会触发测量或更改配置，不能仅凭名字中有 `read` 就允许。首轮优先用操作者面板可对照的身份、配置和现有锁相信号读数；不要求自动发现所有设备。

成功标准：中央看见正确的 PC 与设备身份，收到记录和时间戳，子电脑存在对应本地文件，仪器面板设置与输出状态保持预期。任一设备失败，保留具体错误，不用模拟读数替代真实结果。

### 第二步：逐台小范围验证

在实际接线、负载、允许范围和停止顺序明确后，分别验证一个输出动作、读回和本地停止。先做适合该装置的测试负载验证，再进入样品测量。不从旧代码的电压、电流或光功率值推断新样品允许值。

锁相和 chopper 需要分别核对软件控制路径与物理参考路径；频率、谐波、参考来源及信号单位随实验登记。只有一台锁相时，按其实际可提供的通道和阶段安排采集，不假设它能同时完成全部输运测量。

### 第三步：一个短的组合实验

根据两台 SMU 的实际角色，选择几个点的短实验：固定其他条件 → 施加已批准的一个设置 → 等待稳定 → 读取 SMU 和锁相 → 本地落盘并上传 → 中央显示结果 → 执行已验证的结束步骤。

第一轮先使用固定计划。待驱动、读回、数据格式和停止行为验证后，再实现中央基于质量结果修改下一阶段，例如在上限内增加平均、细化少量扫描点。中央模型负责建议；本地参数限制仍然执行。

### 第四步：停止与网络中断验证

先在已验证的测试装置上检查停止、中途断网、重连和进程重启。确认本地中止/结束动作、记录保留、数据补传和中央状态一致。响应丢失的物理动作不盲目重复；先核对设备实际状态。

现有模拟框架具有 watchdog 与恢复机制，但真实设备的结束动作必须逐型号验证，不能用模拟验收替代实机验收。

## 8. 之后每次实验的配合方式

1. 子电脑启动 Agent，操作者核对装置、接线、样品和限制。
2. 在中央描述本次目标与参数，检查生成的阶段计划。
3. 中央下发任务；子电脑执行、本地保存、上传状态与数据。
4. 操作者在中央查看进度、数据与异常；需要时暂停或停止。
5. 完成后核对装置结束状态，保存实验记录。更换接线时更新装置版本。

因此，当前最有用的下一步是提供**参考代码、设备型号/本机地址、原先可用的环境信息，以及两台电脑之间可访问的中央地址**。据此才能制作这台 PC 的真实接入包；不需要先迁移全部生产环境。
